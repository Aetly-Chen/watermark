## 1. 项目目标与范围

开发一款 Android 去水印工具，第一版支持用户从相册导入图片或视频，手动标记水印区域，执行本地修复，并预览、保存结果。初期不开发账号系统、会员支付和自建云端服务，以降低开发复杂度和运营成本。

### 1.1 MVP 必须具备的功能

**图片**
- 从系统照片选择器导入图片。
- 支持矩形选区和画笔涂抹，标记需要修复的水印区域。
- 将编辑区域转换成 Mask（修复掩码）。
- 使用 OpenCV 的传统图像修复算法进行本地修复。
- 查看原图与结果、重新修复、撤销/重置、保存到相册。
- 对输入尺寸、输出尺寸、处理失败和存储空间不足给出提示。

**视频**
- 导入 MP4 等常见视频格式。
- 展示视频预览、时长和基本媒体信息。
- 支持两类水印：位置固定的（一个 Mask 用全片）与位置逐帧漂移的（逐帧轨迹），见 3.3。
- 对视频帧逐帧应用对应的 Mask 和本地修复算法。
- 水印位置漂移时自动判定并逐帧追踪；追踪不可靠时引导用户补一个关键帧，而不是静默产出残次品。
- 重新编码视频，并尽可能保留原音轨、方向和时间信息。
- 展示处理进度，允许取消任务，完成后预览与保存。

**通用能力**
- 本地处理历史记录。
- 任务状态：等待、处理中、成功、失败、已取消。
- 临时文件管理和缓存清理。
- 处理逻辑与 UI 解耦，为未来本地 AI、云端 AI 预留接口。

### 1.2 第一版明确不做

- 全自动识别水印，完全不依赖用户标注（仍需要用户在首帧框一次）。
- 旋转、缩放等**形变水印**的自动跟随（即 3.3.1 表格里的后两种形态）。
- 承诺任何复杂背景都能无痕恢复。
- 云端任务、账号体系、会员支付和订阅。
- 自建 GPU 服务器。
- 复杂的视频时序 AI 补全。

这些功能可在后续阶段评估，避免 MVP 范围失控。

### 2.2 推荐技术选型

| 层级 | 技术 | 作用 |
|---|---|---|
| 跨平台 UI | Flutter + Dart | 页面、交互、导航、任务状态展示 |
| 状态管理 | Riverpod 或 Bloc（二选一） | 管理编辑状态、任务进度与历史列表 |
| 路由 | go_router 或 Flutter Navigator | 页面导航 |

| 本地图片修复 | OpenCV | Mask、传统 Inpainting |
| 本地视频追踪 | OpenCV | 全局运动估计、稀疏光流、仿射估计、时序中值（见 3.3） |
| Android 原生层 | Kotlin | 媒体处理、线程、平台通道、资源释放 |
| 视频解复用/解码 | MediaExtractor + MediaCodec | 读取音视频轨道、解码视频帧 |
| 视频编码/封装 | MediaCodec + MediaMuxer | 编码视频并封装音频/视频轨道 |
| 本地历史 | SQLite / Drift，或轻量 JSON 元数据 | 保存任务信息，不必复制所有原始媒体 |
| 未来本地 AI | ONNX Runtime Mobile 等候选方案 | 运行经过验证、兼容移动端的模型 |
| 未来后端 | NestJS | API、鉴权、任务管理、限流 |
| 未来 AI 服务 | Python + 合适的推理运行时 | 模型部署与 GPU 推理 |
| 未来任务队列 | Redis + BullMQ 等 | 长任务调度、重试与状态追踪 |
| 未来对象存储 | S3 兼容对象存储 | 临时输入/输出文件 |

**重要说明：**
- Flutter 不负责直接处理所有视频帧；高负载媒体工作放到原生层或后台任务中。
- OpenCV 的传统修复适合小区域、简单背景，不等于 AI 内容恢复。
- Android 的 `MediaCodec` 能力与设备/编码格式有关，必须在真实设备上验证。
- 不建议新项目直接依赖已经退役的原版 FFmpegKit。若未来确实需要 FFmpeg 的格式兼容或滤镜功能，需重新评估维护状态、打包方式和 LGPL/GPL 许可义务。
- 选择任何模型前，都要核对代码、权重、依赖和商业使用许可。

## 3. 核心处理流程

### 3.1 图片去水印

```text
选择图片
  ↓
读取尺寸、方向和格式
  ↓
显示可缩放图片预览
  ↓
用户框选/涂抹水印
  ↓
生成与原图坐标一致的 Mask
  ↓
LocalBasicProcessor
  ↓
OpenCV Inpainting
  ↓
生成临时结果
  ↓
预览 / 重做 / 重置
  ↓
保存到相册并记录历史
```

#### 图片实现要点
1. UI 预览坐标必须准确映射到原图像素坐标，考虑缩放、裁剪、留白和 EXIF 方向。
2. Mask 应与处理图像尺寸一致，通常使用单通道二值图；水印区域为需要修复的区域。
3. 提供修复半径或简单的质量选项，但不要在第一版暴露过多难懂参数。
4. 大图处理需控制内存峰值；不要同时长期保留多份完整解码图像。
5. 原图只读，输出写入独立临时文件，避免破坏用户原始文件。

### 3.2 视频去水印（位置固定的水印）

> 水印位置逐帧变化时见 3.3。两条路径共用同一套解码、逐帧修复、编码与封装流程，区别只在于 Mask 是「一张」还是「一串」。

```text
选择视频
  ↓
读取时长、分辨率、帧率、音轨与旋转信息
  ↓
显示视频预览
  ↓
用户在预览画面框选固定水印
  ↓
将预览坐标映射到视频帧坐标
  ↓
MediaExtractor 读取轨道
  ↓
MediaCodec 解码视频帧
  ↓
逐帧应用对应的 Mask + OpenCV 修复
  ↓
MediaCodec 编码输出视频
  ↓
MediaMuxer 封装视频与可兼容的音轨
  ↓
检查输出文件并预览
  ↓
保存、写入历史、清理临时文件
```

#### 视频实现要点
- 位置固定的水印直接套用同一 Mask；位置逐帧漂移的走 3.3 的追踪流程。两条路径共用一个处理入口，UI 上不要暴露成两个功能。
- 逐帧处理，不要把整个视频解码后一次性放入内存。
- 正确处理帧时间戳、音画同步、旋转方向、帧率和编码器 EOS 状态。
- 重新编码通常会产生画质损失，提供“标准/高质量”等少量选项，并合理设置码率。
- 音频轨道需要单独处理。遇到不支持的编码或容器时，清晰告知用户，而不是静默丢失音频。
- 任务应支持取消，并在取消或失败时释放 `MediaCodec`、`MediaExtractor`、`MediaMuxer` 和临时文件。
- 第一版建议限制输入视频时长、分辨率和文件大小；阈值通过真机测试确定，不要写死成适用于所有设备的承诺。

### 3.3 动态水印（移动水印）去除

> **结论先说：动态水印不是「多标几个框」，而是把选区从「一个矩形」升级成「一组随时间的关键帧」。**

3.2 的流程隐含一个前提——水印位置固定，所以可以「标一帧，把这一个 Mask 复制到 900 帧」。水印一旦移动，这个前提就崩了：在 t=0 准确的框，到 t=20s 会变成「框住了干净的墙、把水印留在框外」。

#### 3.3.1 四种运动形态，处理难度差很远

| 形态 | 特征 | 处理策略 |
|---|---|---|
| **位置漂移** | 位置在动，大小与形状不变 | 3.3.4 关键帧 + 追踪（主力） |
| **周期显隐** | 位置固定，透明度按周期变化 | 位置可按静态处理，但 Mask 必须逐帧给，否则修复处会「时有时无」 |
| **形变跟随** | 旋转、缩放、贴着某个物体走 | 需要稠密光流或逐帧检测，成本最高 |
| **多实例轮播** | 同屏多个水印随机位置出现 | 逐帧检测 + 时序中值兜底 |

第一版覆盖前两种；后两种必须明确标注「效果不保证」，不能靠 UI 文案暗示能做到。

#### 3.3.2 先分诊，再选路线

不要一上来就跑最重的算法。先用全局运动估计把视频分成两类：

```text
对相邻帧估计全局运动（全景单应 H 或全局光流）
  ├── 镜头静止（H ≈ I）  →  快速路径：时序重建（3.3.3）
  └── 镜头在运动        →  主力路径：关键帧 + 追踪（3.3.4）
```

这个判断是纯 CPU 的，可在数百毫秒内完成，却能省掉大量无谓计算。

#### 3.3.3 快速路径：时序中值重建

**这是动态水印相对静止水印的一个真实优势。** 水印既然在移动，它就不会一直盖住同一个像素——同一块背景在别的时刻是干净的。把它们按时间轴取分位数，背景自己就浮出来了。

三条硬门槛，缺一不可：

1. 镜头基本静止（全局运动低于阈值）。
2. 水印确实在移动（静止水印会在中值里占多数，重建不出来）。
3. 在重建窗口内，每个像素被水印覆盖的帧数占比 < 50%。

```text
for 每个像素 (x, y) in 选区:
    samples = [ F[t][x][y] for t in 时间窗 ]      # 例如 ±7 帧
    samples.sort()
    background[x][y] = samples[分位数]            # 通常取中位数
M[t] = 选区 ∧ (|F[t] - background| > 差异阈值)
```

- **优点**：纯 CPU、可离线，比逐帧修复快一个量级；而且结果天然没有时序闪烁（背景始终是同一张）。
- **代价**：背景本身有运动物体（行人、树叶、水面）时会出现残影，必须在 UI 上如实告知。
- **实现注意**：不要一次把整个窗口的帧都解码驻留，内存峰值会炸；滑动窗口应增量维护。

#### 3.3.4 主力路径：关键帧标注 + 光流追踪

用户只标 2~3 个关键帧，中间的帧由追踪算出来。

**为什么用稀疏光流而不是逐帧检测**：追踪在时序上连续，不会像检测那样「这一帧找到、下一帧找不到」而产生闪烁；且稀疏光流的计算量远低于逐帧模板匹配。

```text
输入：帧序列 F[0..N-1]，关键帧 K = {(t_i, box_i)}
输出：每帧的水印框 perFrameBox[0..N-1]

for 每一对相邻关键帧 (K_i, K_{i+1}):
    pts = goodFeaturesToTrack(F[t_i], mask = box_i)          # 只在框内取点
    for t in (t_i, t_{i+1}]:
        pts', status = calcOpticalFlowPyrLK(F[t-1], F[t], pts)
        pts''        = calcOpticalFlowPyrLK(F[t], F[t-1], pts')   # 反向校验
        丢弃 |pts'' - pts| > 1.0 px 的点                          # 前后不一致 = 不可靠
        A, inliers = estimateAffinePartial2D(pts_good, pts'_good, RANSAC)
        if inliers < 阈值:
            quality[t] = needsKeyframe        # 交给 UI 提示用户补一帧
            continue
        perFrameBox[t] = A · box_i
```

三个必须做的工程细节：

1. **反向校验（前向-后向误差）**：省掉这一步，被遮挡或出画的特征点会污染仿射估计，框会缓慢漂移。
2. **时间平滑**：对 `perFrameBox` 序列做中值滤波 + 线性插值。框在抖，比框略偏更难看。
3. **漂移要有出口**：内点数持续低于阈值时必须**停下来问用户**，而不是硬算到底。UI 上对应「这一段追踪不可靠，请在 00:14 附近补一个关键帧」。

性能：稀疏光流是纯 CPU，1080p 每帧通常在个位数毫秒量级，但**必须在中低端真机上实测**，不要按开发机的数字做承诺。

#### 3.3.5 兜底路径：逐帧检测

只在追踪置信度崩溃、且用户不愿补关键帧时启用。用归一化互相关（`cv::matchTemplate`）+ 多尺度搜索，在上一帧位置附近的小窗口内找水印。

- 适合：外观不变、只平移的水印。
- 不适合：旋转、缩放、半透明叠加在复杂纹理上。
- 成本：每帧一次模板匹配，明显比稀疏光流贵。

#### 3.3.6 明确不做：云端时序补全

ProPainter、E2FGVI 这类视频时序补全模型能给出最连贯的结果，但需要 GPU，也需要上传。

**MVP 不接入，也不在 UI 上暗示具备这个能力。** 只有同时满足以下条件才考虑：逐帧修复在真实样本上出现肉眼可见的闪烁，且有用户明确愿意上传素材。届时它必须是一个显式的「上传到云端处理」选项，绝不默认触发。

#### 3.3.7 处理流水线（动态）

```text
选择视频
  ↓
读取时长、分辨率、帧率、音轨与旋转信息
  ↓
用户在预览里框出水印（第一帧）
  ↓
全局运动分诊
  ├── 镜头静止 → 时序重建 → 生成逐帧 Mask
  └── 镜头运动 → 引导用户补 1~2 个关键帧
                   ↓
                稀疏光流传播 + 反向校验 + 时间平滑
                   ↓
                置信度不足 → 回到「请补关键帧」
                   ↓
                生成逐帧 Mask 序列
  ↓
逐帧修复（复用 3.2 的 OpenCV 修复，但每帧 Mask 不同）
  ↓
时序一致性检查（相邻帧修复区域差异过大 → 标记并提示）
  ↓
编码 → 封装音轨 → 预览（必须支持播放对比）→ 保存
```

#### 3.3.8 抑制时序闪烁

动态水印最典型的翻车不是「修不干净」，而是「修得忽明忽暗」。三个手段：

1. **Mask 时间平滑**：对框序列低通，避免 Mask 边界逐帧跳动。
2. **修复区域与原帧羽化混合**：边界做 alpha 过渡，硬切会产生可见方块。
3. **相邻帧结果滑动平均**：只在水印区域内做，窗口控制在 3 帧以内，否则产生拖影。

#### 3.3.9 接口扩展

现有 `ProcessingRequest` 用一个 `maskPath` 表达修复范围——**这只能表达静态水印**。动态水印需要把「范围」从一个文件变成一条轨迹：

```dart
/// 水印在整段视频里的运动方式
enum WatermarkMotion {
  staticFixed,   // 位置固定：一个 Mask 用全片
  drifting,      // 位置漂移：需要轨迹
  occluded,      // 形变 / 遮挡：第一版不做，返回明确的不支持错误
}

/// 关键帧：用户在某一时刻框出的水印位置
class Keyframe {
  final Duration time;
  final Rect box;          // 归一化到源帧 0..1，与分辨率无关
  final double confidence; // 1.0 表示人工标注
  const Keyframe(this.time, this.box, {this.confidence = 1.0});
}

enum TrackQuality { good, drifted, needsKeyframe }

/// 逐帧修复计划
class MaskPlan {
  final WatermarkMotion motion;
  final List<Keyframe> keyframes;  // 用户标注 + 追踪失败时补的
  final List<Rect>? perFrameBox;   // 长度 == 总帧数；staticFixed 时为 null
  final String? staticMaskPath;    // 仅 motion == staticFixed 时使用
  final TrackQuality quality;
  const MaskPlan({
    required this.motion,
    required this.keyframes,
    this.perFrameBox,
    this.staticMaskPath,
    this.quality = TrackQuality.good,
  });
}

class ProcessingRequest {
  final String taskId;
  final String inputPath;
  final String outputPath;
  final MaskPlan plan;   // ← 替代原来的单一 maskPath
  // ... 其余字段不变
}
```

要点：

- `box` 一律用**归一化坐标**存储，避免分辨率或旋转方向变化后整条轨迹作废。
- `perFrameBox` 的长度必须等于总帧数。长度对不上是这类实现最常见的崩溃点，要在入口处断言。
- `quality == needsKeyframe` 必须能被 UI 读到，否则用户只会看到「处理完了但没修干净」。

#### 3.3.10 性能与限制

- 动态水印的耗时通常是静态的 **1.6~2.5 倍**（追踪开销 + 每帧 Mask 不同导致无法复用中间结果）。具体倍数必须实测。
- 输入限制要比静态更严：建议对动态水印单独设更短的时长上限，因为追踪失败重来的代价更高。
- 明确不承诺的场景：复杂纹理背景 + 大位移 + 镜头本身也在运动。

#### 3.3.11 验收标准（动态水印）

- **无残留**：整段视频抽样 30 帧，人工检查水印可见的比例，目标为全部不可见。
- **无闪烁**：相邻帧修复区域的平均绝对差低于阈值（阈值用一段已知干净的视频标定）。
- **轨迹准确**：追踪框中心与真实水印中心的偏差，在整段里不持续超过水印宽度的 1/4。
- **有出口**：追踪置信度不足时，UI 能收到 `needsKeyframe` 并引导用户补标注，而不是静默产出残次品。
- **可取消**：取消后释放 `MediaCodec` / `MediaExtractor` / `MediaMuxer`、追踪中间态与临时文件。
- **可降级**：时序重建的门槛不满足时，必须自动回退到关键帧追踪，而不是产出一张错误的背景图。

#### 3.3.12 对应的 UI 变化

动态水印在界面上不是加几个参数，而是新增几样东西（已在 `ui/` 下的原型中体现）：

| 元素 | 作用 |
|---|---|
| **时间轴关键帧标记** | 菱形标记，可拖动改时间、点击跳到该帧；这是用户唯一需要手动干预的地方 |
| **选框状态区分** | 关键帧上选框四角实心（可编辑）；追踪出来的帧四角空心（只读）。不用文字解释，看框角形状就知道能不能改 |
| **播放对比** | 静态的「修复前 / 修复后」分界线不够用，必须能**边播边看**，才会发现闪烁与跳变 |
| **处理阶段拆分** | 进度页要区分「分析镜头运动 / 追踪水印轨迹」，否则动态任务看起来像卡住了 |
| **追踪状态提示** | 媒体区上直接给结论：「已自动追踪 · 3 个关键帧」 |

另外，**不要让用户选路线**。「水印位置固定」是一个内部假设，而用户并不知道自己的视频属于哪一类。识别阶段自动判定，界面只呈现结论；把「静止 / 跟随」保留成一个可以手动覆盖的开关即可。

### 4.1 处理接口草案

```dart
enum MediaKind { image, video }

enum ProcessingMode {
  localBasic,
  localAi,
  cloudAi,
}

enum ProcessingStatus {
  queued,
  running,
  succeeded,
  failed,
  cancelled,
}

class ProcessingRequest {
  final String taskId;
  final String inputPath;
  final String outputPath;
  final MediaKind mediaKind;
  final ProcessingMode mode;
  final String maskPath;

  const ProcessingRequest({
    required this.taskId,
    required this.inputPath,
    required this.outputPath,
    required this.mediaKind,
    required this.mode,
    required this.maskPath,
  });
}

class ProcessingResult {
  final String outputPath;
  final int? outputWidth;
  final int? outputHeight;
  final Duration? outputDuration;

  const ProcessingResult({
    required this.outputPath,
    this.outputWidth,
    this.outputHeight,
    this.outputDuration,
  });
}

abstract interface class WatermarkProcessor {
  Future<ProcessingResult> process(ProcessingRequest request);
  Future<void> cancel(String taskId);
}
```

> **注意：上面这段接口表达不了动态水印。** `maskPath` 只能描述「一个 Mask 用全片」；位置漂移的水印需要一条逐帧轨迹，按 3.3.9 的 `MaskPlan` 结构扩展。即便第一版只跑静态水印，也应该先把数据结构留好——这件事在静态阶段就会定型，等到做动态水印时才发现接口装不下，就得回头改整条链路。

这是接口设计草案，不是完整可直接运行的代码。实际实现还需要进度流、错误类型、资源清理、重试策略和平台通道通信。

## 7. AI 模型与算法选择

### 7.1 第一版

优先使用 OpenCV Inpainting（例如 Telea 或 Navier–Stokes 方法）作为本地基础修复。它实现成本低、无需 GPU，但对复杂纹理和较大遮挡区域的效果有限。

### 7.2 本地 AI 候选

LaMa 等图像补全模型可以作为评估对象，但不能直接假设模型一定能在 Android 上高效运行。必须验证：
- 权重和代码许可是否允许预期的商业用途。
- 模型是否可导出到目标推理运行时。
- 算子支持是否完整。
- 模型大小、RAM 峰值、CPU/GPU/NPU 执行表现。
- 真实测试图片的修复质量。
- APK/AAB 增量大小和首次加载时间。

ONNX Runtime Mobile 是一个候选推理运行时，不代表任意模型都可以直接运行。需以目标模型的转换结果和真机测试为准。

### 7.3 视频 AI

视频的难点不仅是单帧修复，还包括连续帧一致性。逐帧运行图片模型可能造成闪烁、拖影或细节跳变。因此建议：
1. MVP 使用传统修复：静态水印单 Mask、动态水印走 3.3 的追踪流程，两者都不依赖 AI 模型。
2. 先验证真实设备的吞吐量、内存和音画同步。
3. 后续再比较逐帧模型与具备时序信息的模型。
4. 只有在成本和效果可接受时才加入云端视频 AI。

**注意区分两类「AI」，不要混为一谈：** 3.3 的追踪方案（全局运动估计、稀疏光流、仿射估计、时序中值）全部是**经典计算机视觉算法**，不引入模型、不增加 APK 体积、可完全离线，应当作为 MVP 的一部分交付。本节讨论的是另一件事——用生成式模型替代传统修复，以换取复杂背景下的补全质量。这是后续阶段的事。

## 8. 成本策略

### 8.1 MVP 成本

如果已有开发电脑和 Android 测试机，初期可以把额外运行成本压到接近零：

| 项目 | 初期成本策略 |
|---|---|
| Flutter / Android Studio | 免费开发工具 |
| OpenCV | 可免费使用，遵守许可证 |
| Android 媒体 API | 系统提供 |
| 本地历史与文件 | 使用设备存储 |
| 自建服务器 | 不需要 |
| GPU | 不需要 |
| 云端 API | MVP 不接入 |

### 8.2 后续云端成本

云端成本取决于供应商、模型、GPU、输入输出大小、任务时长、存储和流量。不要把任何单一 GPU 小时价格直接当成“每个任务总成本”。

粗略估算可用：

```text
每任务计算成本
≈ GPU 每小时单价 × 单任务实际 GPU 占用秒数 / 3600

总成本
≈ 计算成本 + 输入/输出流量 + 临时存储 + API/队列/监控费用
```

建议先收集实际任务数据，再决定按量 GPU、托管推理 API 或自建 GPU 服务。低使用量阶段优先避免长期包月 GPU 资源。

## 9. 隐私、安全与授权

- 默认本地处理，图片和视频不会自动上传。
- 云端功能必须由用户主动选择，并明确说明上传范围与保留期限。
- 临时文件采用随机名称，处理结束后按策略清理。
- 不在普通日志中保存原始图片、视频内容或敏感路径。
- 云端 API 必须验证任务归属，避免通过猜测任务 ID 读取他人结果。
- 上传服务应验证文件实际格式、大小、时长和解码结果，不能只信任扩展名。
- 对长任务设置超时、并发限制和取消机制。
- 只处理用户拥有或有权修改的素材；不要承诺能真实恢复被遮挡的原始内容。
- 在集成模型或媒体库前核对代码、权重、依赖和分发许可证。
- 上架前准备隐私政策、数据删除说明、商店数据安全披露与所需的权限说明。

## 10. MVP 验收标准

### 图片
- 可以从系统照片选择器导入常见图片。
- 选区映射准确，缩放或平移后仍对应正确的原图位置。
- Mask 可重置，处理失败不会覆盖原图。
- 成功生成并保存处理结果。
- 对超大图或内存不足给出明确提示，不崩溃。

### 视频
- 可导入并读取目标测试设备支持的 MP4 视频。
- 固定位置水印可应用于所有视频帧。
- 动态水印按 3.3.11 单独验收（无残留 / 无闪烁 / 轨迹准确 / 有出口 / 可降级）。
- 导出结果可播放，音轨在兼容情况下保留。
- 处理进度可见，取消后能释放资源并清理临时文件。
- 测试旋转方向、不同帧率、无音轨视频、长视频和低存储空间场景。
- 对不支持的编码提供清楚提示。

### 工程质量
- UI 不因媒体处理而卡死。
- 任务状态统一，重复提交得到妥善处理。
- 处理成功、失败和取消均有明确结果。
- 代码按功能模块划分，处理引擎通过接口隔离。
- 没有服务器依赖；断网仍可完成本地基础流程。

## 11. 推荐开发顺序

1. 安装 Flutter、Android Studio 与 Android SDK，创建空项目。
2. 搭建首页、图片选择、视频选择和基础路由。
3. 先完成图片：选区 → Mask → OpenCV → 预览 → 保存。
4. 验证 Kotlin 与 Flutter 的平台通道，并处理线程与资源生命周期。
5. 完成视频元信息、预览、选区与坐标映射。
6. 实现静态水印的逐帧修复、编码、音轨封装、进度和取消。
7. 接入动态水印：先做全局运动分诊与关键帧数据结构（3.3.2 / 3.3.9），再做稀疏光流追踪（3.3.4），最后补时序中值的快速路径（3.3.3）。
8. 增加本地历史、缓存清理、异常处理。
9. 在真实 Android 设备上测试不同分辨率和性能档位，并按 3.3.11 单独验收动态水印。
10. 收集样本并评估本地 AI 模型。
11. 只有确实需要云端处理时，再增加后端与 AI Worker。

### 最终建议

第一版使用 **Flutter + Kotlin + OpenCV + Android MediaExtractor / MediaCodec / MediaMuxer**。不租服务器，不先做账号系统；先完成图片与视频本地闭环。代码通过 `WatermarkProcessor` 抽象隔离本地实现，后续按需添加本地 AI 和云端 AI。

视频侧要一次做对的是**数据模型**：修复范围要从「一个 Mask 文件」变成「一条逐帧轨迹」（3.3.9）。这件事在静态水印阶段就会定型，等做动态水印时才发现接口表达不了，就得回头改整条链路。所以即便第一版只跑静态水印，`MaskPlan` 也应该先按 3.3.9 的形状留好。

这条路线可以控制前期成本，也能避免以后扩展时重写主要 UI 与业务流程。
